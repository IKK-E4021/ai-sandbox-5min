AI Sandbox ― 5分でわかる図解

AIを信用しきらなくても使えるように、「暴走してもここまで」という境界を先に作る。

Sandboxなし

AI Agent がコードを読む
↓
Shell / Git / Browser / Network を実行
↓
誤操作・Prompt Injection
↓
Host / ~/.ssh / ~/.aws / 社内NW まで被害が波及
AI Sandbox
AI専用の「安全な作業部屋」
部屋の中では自由に動かす。
でも、外には勝手に出さない。
Blast Radius を小さくする

Sandboxあり

  • Workspace内は読み書きOK
  • Host側の秘密情報は触らせない
  • Networkは必要先だけ許可
  • 危険なOS操作はKernel側で拒否
  • 壊れたら環境ごと捨てる

AIへのお願いではなく、OS / Container / VM 側で強制するのが重要。

Sandboxで制御する5つの軸
1. Filesystemどのファイルを読める・書けるか。
例：/workspaceのみRW。
2. Networkどこへ通信できるか。
外部送信や社内NW到達を制限。
3. PermissionどのOS機能・コマンドを使えるか。
4. CredentialAWS / GitHub / SSHなどの秘密情報をどう隔離するか。
5. Lifetime環境を使い捨てにし、壊れても作り直せるか。
OSレベルの代表的な仕組み
Seatbelt
macOS
プロセス全体をSandbox化
ファイル・ネットワークなどのアクセスをポリシーで制限。macOS版Codex / Claude Codeなどで使われる。
seccomp
Linux
「何をしてよいか」を制限
mount() や ptrace() など、危険なSystem CallをKernel側で拒否する。
Landlock
Linux
「どこにしてよいか」を制限
/workspace はOK、~/.ssh はNGなど、Filesystemへのアクセス範囲を限定する。
Coding Agentの例
Codex
Sandbox内はある程度自由に動かし、境界を越える操作だけ承認させる考え方。
Claude Code
毎回確認するより、安全な範囲を先に決めて、その中では自由に動かす方向。
GitHub Copilot Coding Agent
クラウドの一時的な実行環境で実装・テストし、PRを作成。作業後は環境を破棄。
AI Sandbox = 「AIが正しいことを期待する」のではなく、
「間違っても、ここまでしか壊せない」を環境側で保証する仕組み
